> [놀러와마이홈 게임 계산기](/projects/game-calculator)

「놀러와마이홈」은 재료를 모아 물품을 만드는 게임이다. 물품 하나를 만들려면 재료가 필요하고, 그 재료가 다시 다른 물품인 경우가 많다. 계산기가 하는 일은 단순하다. **물품을 시장에서 살 수 있는 기본 재료까지 끝까지 펼쳐서, 기본 재료별 수량과 가격을 구하는 것.**

2023년에 NestJS로 만든 이 계산 로직을 2026년 백엔드를 Django로 옮기면서 다시 썼다. 조건은 하나였다. **프론트엔드와 DB를 건드리지 않는다.** 응답의 재료 순서까지 이전과 같아야 화면이 그대로 동작한다. 이 글은 알고리즘을 바꾸면서 결과를 그대로 지킨 방법을 정리한 것이다.

## 1. 문제: 레시피는 트리가 아니라 DAG다

예를 들어 이런 레시피가 있다고 하자.

```plaintext
식탁 = 판자 ×2 + 못 ×4
판자 = 나무 ×3
의자 = 판자 ×1 + 나무 ×2
```

`식탁`을 펼치면 `못 4, 나무 6`이 된다. 하위 수량에는 부모 수량을 곱한다. 여기까지는 트리 순회다.

하지만 실제 데이터에서는 `판자` 같은 중간 물품을 여러 물품이 함께 쓴다. 그래서 구조가 트리가 아니라 **DAG**(방향 비순환 그래프)이고, 관리자가 잘못 입력하면 순환(`A → B → A`)도 생긴다.

## 2. 기존 구현: 큐 기반 BFS

기존 NestJS 구현의 뼈대는 다음과 같았다 (요약).

```ts
let queue = materials.filter((m) => !m.basic);
const endMaterials = materials.filter((m) => m.basic);

while (queue.length !== 0) {
  for (const product of allProducts) {          // ① 매번 전체 물품을 선형 탐색
    if (queue[0].name === product.name) {
      for (const material of product.materials) {
        queue.push({ ...material, count: queue[0].count * material.count });
      }
      queue = queue.slice(1);
      break;
    }
  }
  if (queue[0]?.basic) {
    addBasic(queue[0], endMaterials);           // ② 같은 이름이 있으면 count를 더함
    queue = queue.slice(1);
  }
}
```

동작은 맞았지만 문제가 넷 있었다.

1. **매 단계 전체 물품 선형 탐색.** 큐에서 하나를 꺼낼 때마다 전체 물품 목록을 돈다.
2. **같은 하위 물품을 계속 다시 펼친다.** `판자`를 쓰는 물품이 100개면 `판자`도 100번 펼친다. 전체 물품의 결과를 한꺼번에 다시 계산할 때(시세 수정 시) 이 비용이 곱해진다.
3. **입력 오염.** `endMaterials`의 초기값은 입력 재료 객체 그 자체였다. 같은 이름의 재료가 또 나오면 `endMaterials[i].count += ...`로 **원본 재료 객체의 count를 직접 바꿨다.** 한 요청에서 여러 물품을 연달아 계산하면 앞 계산이 뒤 계산의 입력을 망가뜨렸다.
4. **무한 루프.** 이름 검증은 맨 위 단계 재료만 했다. 하위 단계에 없는 물품명이 있으면 큐가 줄지 않았고, 순환 레시피도 큐가 끝없이 늘었다. 둘 다 서버가 응답하지 않는 상태가 됐다.

## 3. 바꾼 방식: 물품별 메모이제이션 DFS

새 계산기는 세 가지를 바꿨다.

- 물품·시세를 **이름 → 값 dict**로 찾는다. 선형 탐색이 없어진다.
- 물품마다 펼친 결과를 **한 번만 계산해 메모**한다. 하위 물품을 몇 개 물품이 쓰든, 전체 물품을 한꺼번에 계산하든 각 물품은 한 번만 펼친다.
- 입력은 `frozen` dataclass로 받고, 결과는 새 dict에만 쌓는다. **입력을 바꿀 수 없다.**

DFS로 바꾸면 순환 감지도 쉽다. 지금 펼치고 있는 경로(`_expanding`)에 같은 물품이 또 나오면 순환이다. 경로를 메시지에 그대로 넣어서 관리자가 어디가 잘못됐는지 바로 알 수 있게 했다.

```python
def _expand(self, name):
    if name in self._levels:                 # 메모 적중
        return self._levels[name]
    if name in self._expanding:              # 펼치는 중인 물품을 또 만나면 순환
        path = " → ".join([*self._expanding[self._expanding.index(name):], name])
        raise CircularRecipeError(f"재료 구성에 순환 참조가 있습니다. ({path})")

    recipe = self._recipes.get(name)
    if recipe is None:                       # 없는 하위 물품명
        raise UnknownMaterialError(...)

    self._expanding.append(name)
    try:
        ...  # 아래 4장
    finally:
        self._expanding.pop()
```

예전에는 서버가 멈추던 두 경우가 이제는 사람이 읽을 수 있는 메시지를 담은 예외가 된다. 물품을 저장할 때 이 예외가 나면 저장을 거절하고, 이미 들어간 데이터라면 관리자용 데이터 점검 화면에 문제로 나타난다.

## 4. 어려운 부분: DFS로 BFS의 순서를 재현하기

여기서 걸리는 게 있었다. 응답의 재료 목록은 **처음 등장한 순서**대로 나간다. 기존 BFS에서 그 순서는 이렇다.

- 얕은 단계의 재료가 먼저 나온다.
- 같은 단계 안에서는 레시피에 적힌 순서를 따른다.

DFS로 그냥 펼치면 깊은 재료가 먼저 튀어나와 순서가 바뀐다. 수량과 가격이 같아도 화면의 표 순서가 바뀌면 "API 호환"이 아니다.

그래서 물품마다 메모하는 값을 **합계 하나가 아니라 단계(깊이)별 합계 묶음**으로 했다.

```python
# levels[0] = 레시피에 바로 적힌 기본 재료
# levels[1] = 한 단계 아래 물품을 펼쳐서 나온 기본 재료 ...
direct: dict[str, float] = {}
deeper: list[dict[str, float]] = []

for ingredient in recipe:
    if ingredient.basic:
        accumulate(direct, {ingredient.name: ingredient.count})
        continue
    sub_levels = self._expand(ingredient.name)
    # 하위 물품의 i단계는 이 물품의 i+1단계가 된다
    deeper.extend({} for _ in range(len(sub_levels) - len(deeper)))
    for target, level in zip(deeper, sub_levels):
        accumulate(target, level, factor=ingredient.count)

levels = (direct, *deeper)
self._levels[name] = levels
```

최종 결과는 단계 0부터 순서대로 하나의 dict에 합친다. Python dict는 삽입 순서를 지키기 때문에 이것만으로 **"얕은 단계 먼저, 같은 단계는 레시피 순서"**가 된다. 하위 물품의 단계 묶음은 메모해 둔 값을 재사용하고 부모 수량만 곱한다. 그래서 순서를 지키면서도 각 물품은 한 번만 펼친다.

여기서 고민한 것은 "순서를 그냥 바꾸고 프론트에서 정렬하면 되지 않나"였다. 하지만 그러면 이번 전환의 원칙(프론트·DB 무변경)이 깨지고, 순서가 바뀐 이유가 버그인지 의도인지 구분할 수 없게 된다. 순서도 계약의 일부로 보고 지키기로 했다.

## 5. 검증: 레거시 코드를 정답지로 쓰기

알고리즘을 바꿨으니 "예전과 결과가 같다"를 증명해야 했다. 손으로 쓴 테스트 케이스 몇 개로는 부족하다. 순서가 어긋나는 경우는 대개 하위 물품을 공유하는 복잡한 레시피에서만 나오기 때문이다.

그래서 **레거시 TypeScript 계산 코드를 그대로 트랜스파일해서 정답지로** 썼다.

1. 시드를 고정한 난수로 레시피를 만든다. 물품 3~40개, 깊이 1~6, 하위 물품 공유, 정수·소수 수량을 섞는다.
2. 같은 입력을 레거시 코드에 넣어 결과를 뽑아 **골든 fixture**(`legacy_golden.json`, 시나리오 50개·물품 720개)로 저장한다.
3. 새 계산기 결과의 **재료 이름 순서, 수량, 가격, 총액**이 fixture와 같은지 pytest로 비교한다.

부동소수점 오차는 곱셈·덧셈 순서가 달라 생기는 차이만 허용했다(상대 오차 `1e-9`). 순서는 오차 없이 완전히 같아야 통과한다.

레거시 쪽에는 3장의 입력 오염 버그가 있다. 그래서 fixture를 만들 때는 물품마다 입력을 깊은 복사해서 돌렸다. 버그까지 정답으로 박제하지 않기 위해서다.

fixture와 별도로 같은 방식의 **차등 퍼징을 3,000개 시나리오**로 돌렸다. 일반 레시피에서 물품 51,762개의 순서·수량·가격이 전부 일치했다. 순환 레시피처럼 레거시가 멈추는 경우는 비교 대상에서 빼고, 별도 단위 테스트로 새 동작(예외)을 고정했다.

메모이제이션이 있으면 하나 더 확인해야 한다. **계산 순서에 따라 결과가 달라지면 안 된다.** 같은 계산기로 정방향·역방향으로 계산한 결과와 매번 새 계산기로 계산한 결과가 모두 같은지 시나리오마다 확인하는 테스트를 넣었다. 레시피 조회 횟수를 세는 dict를 끼워서, 공유 하위 물품을 실제로 한 번만 펼치는지도 단위 테스트로 확인했다.

## 6. 정리

| | 기존 (NestJS) | 새 계산기 (Django) |
| --- | --- | --- |
| 탐색 | 큐 BFS, 매 단계 전체 물품 선형 탐색 | DFS, 이름 dict 조회 |
| 공유 하위 물품 | 쓰일 때마다 다시 펼침 | 물품별 메모, 한 번만 펼침 |
| 재료 순서 | BFS 등장 순서 | 단계별 메모로 같은 순서 재현 |
| 입력 | 재료 객체 count를 직접 변경 | 불변 입력, 새 dict에만 누적 |
| 잘못된 하위 물품·순환 | 무한 루프 | 경로를 담은 예외 → 저장 거절·데이터 점검 |
| 검증 | — | 레거시 골든 fixture + 차등 퍼징 3,000개 시나리오 |

배운 점은 두 가지다.

- **"결과가 같다"의 범위를 먼저 정해야 한다.** 이번에는 수량·가격뿐 아니라 순서까지 계약에 넣었다. 그 결정이 메모 구조(합계 하나 → 단계별 묶음)를 정했다.
- **레거시 코드는 가장 좋은 테스트 오라클이다.** 명세가 없는 오래된 코드라도, 그 코드를 그대로 돌린 결과는 "지금 사용자가 보는 값"이라는 가장 정확한 명세다. 단, 알려진 버그는 정답에서 걸러내야 한다.
